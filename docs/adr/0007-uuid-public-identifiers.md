# 0007. UUIDs as public identifiers, numeric IDs internally

- Status: Accepted
- Date: 2026-10-23

## Context

Sequential numeric identifiers in URLs reveal how many crimes exist and make enumeration trivial. They are, however, efficient as primary keys and foreign keys.

## Decision

Each crime has a numeric `id` (`BIGSERIAL` primary key, used internally) and a `uuid` (random UUID v4, unique, generated by the server). URLs and path parameters use only the `uuid`. The numeric `id` is returned in responses but never accepted as input.

## Alternatives considered

### UUID as the primary key

One identifier instead of two. Random UUID primary keys fragment B-tree indexes and are larger in foreign keys.

### Numeric IDs everywhere

Simplest. It exposes the size of the dataset and allows enumeration.

## Consequences

### Positive

- Public identifiers are not guessable.
- Joins and indexes stay compact.

### Negative

- Two identifiers to keep straight. Requests with a numeric `id` in the path return "not found", which can confuse clients.

### Risks and mitigations

- *Returning the numeric `id` invites clients to use it.* Mitigation: the spec states it is never accepted as input (§3.1). Removing it from responses would need a spec change.
