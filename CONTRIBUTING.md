# Contributing to Crime Map Backend

Thanks for your interest. The API works end to end, and the remaining gaps against the spec are tracked in the [v1 plan](docs/plan/v1.md). Feedback and contributions are welcome.

By participating you agree to the [Code of Conduct](CODE_OF_CONDUCT.md).

## How the project works: Spec-Driven Development

Behavior is specified before it is implemented:

1. **Vision** ([docs/vision.md](docs/vision.md)): why the project exists, its principles and its non-goals.
2. **Spec** ([docs/spec/core.md](docs/spec/core.md)): what the API does, including numbered acceptance criteria (`AC-xx`) and which ones are met.
3. **ADRs** ([docs/adr/](docs/adr/README.md)): why the significant decisions were made.
4. **Code**: implements the spec and is verified by tests that reference the acceptance criteria.

Changes flow in that order. A pull request that adds behavior not described in the spec will be asked to update the spec first.

## Ways to contribute

- **Report a bug or propose a feature** using the [issue forms](https://github.com/pmlucero/go-crime_map_backend/issues/new/choose).
- **Close a gap.** Pick a criterion marked `Not met` in spec §9, following the milestone order in the [plan](docs/plan/v1.md). Comment on its issue, or open one, before starting.
- **Challenge a design decision.** Open an issue that references the ADR or spec section. Accepted ADRs can be challenged too: a good argument leads to a new ADR that supersedes the old one (ADR 0000).
- **Propose a spec change.** Open an issue first for anything non-trivial. Then send a PR that changes only `docs/spec/` (plus the spec version in the `docs/plan/v1.md` header, which follows it), and explain the motivation and how acceptance criteria are affected. The spec stays `Approved` while a change is under review. When the change is merged, it bumps `Version` (minor while the version is below 1.0, e.g. 0.1 → 0.2) and `Last updated`. Marking a criterion `Met` is not a spec change and does not bump the version.
- **Propose an ADR.** Copy the template in [docs/adr/README.md](docs/adr/README.md), use the next free number, set the status to `Proposed`, and add it to the index. An ADR is needed for changes to the HTTP contract, the data model or schema, authentication, the layer structure, or new dependencies.

Please read the [non-goals](docs/vision.md#4-non-goals) before proposing features.

## Pull requests

- Changes to `docs/spec/`, `docs/adr/`, the database schema and `.github/CODEOWNERS` require review from the maintainer (see [CODEOWNERS](.github/CODEOWNERS)).
- All PRs to `main` need an approving review. Fill in the PR template: the traceability section (spec sections, AC-xx, ADRs) is what reviewers look at first.
- CI must pass. It checks Markdown style (`markdownlint-cli2`, configured in `.markdownlint-cli2.jsonc`), internal links and ADR consistency (`.github/scripts/check_docs.py`), the PR title and branch name formats, `go vet`, the tests against PostgreSQL, and `golangci-lint`. PR titles generated by GitHub's Revert button are accepted as-is, and Dependabot titles are exempt from the 72-character limit (their format is still checked). Run the docs checks locally with:

  ```sh
  npx markdownlint-cli2 "**/*.md"
  python3 .github/scripts/check_docs.py
  ```

- Every PR from a branch of this repository gets an advisory review from Claude, following [docs/review-guidelines.md](docs/review-guidelines.md). It does not block merging. Maintainers can request another pass by commenting `@claude review`. PRs from forks are reviewed by the maintainer.
- Keep PRs focused. A spec change, an ADR and an implementation belong in separate commits, and preferably in separate PRs.

### Branches and releases

The project uses **trunk-based development**. `main` is the only long-lived branch, and it is always releasable.

- Work happens on short-lived branches cut from `main` and merged back through a PR. Rebase or merge `main` often, and keep branches to days, not weeks.
- Branch names are `<type>/<kebab-case-description>`. The types are the same as for commits: `feat/`, `fix/`, `docs/`, `test/`, `refactor/`, `chore/`. Example: `fix/not-found-status-codes`. CI enforces this (`branch-name` check) for branches of this repository. PRs from forks are exempt, and so are branches generated by GitHub's Revert button (`revert-…`) and by Dependabot (`dependabot/…`).
- **Urgent fixes** are ordinary `fix/` branches from `main`, prioritized for review. There is no separate hotfix flow.
- **Releases** are tags `vX.Y.Z` (Semantic Versioning) on `main`.

Why not GitFlow (`develop`, `hotfix/`, `release/` per version)? It fits scheduled releases with several supported versions in parallel. Here it would add double merges and divergence between `develop` and `main`. That divergence actually happened in this repository before it moved to trunk-based development.

### Commits

- One logical change per commit.
- [Conventional Commits](https://www.conventionalcommits.org/): `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`, with an optional scope, e.g. `fix(api): return 404 for unknown crimes`.
- The subject is imperative and at most 72 characters. The body explains *why* and references `AC-xx` or `ADR NNNN` when relevant.

### Code

Go conventions, the package layout and testing rules are in [CLAUDE.md](CLAUDE.md). That file is written for coding agents, and the same rules apply to humans. In short:

- `go mod tidy -diff`, `go vet ./...`, `go test -race -p 1 ./...` and `golangci-lint run` must pass, on Go 1.26 and 1.27. Use golangci-lint v2.14.0, the version CI uses (`.github/workflows/go.yml`).
- Integration tests need PostgreSQL. See the README, *Testing*.
- Tests that verify an acceptance criterion reference it (`// AC-12`).
- Optional: install the pre-commit hooks with `pre-commit install`.

### Dependencies

- GitHub Actions are pinned to a full commit SHA, with the version in a comment (`# v1.2.3`).
- New dependencies and version bumps use releases that are **at least 14 days old**, so that bugs or a compromised release have time to surface. Dependabot applies the same rule (`cooldown` in `.github/dependabot.yml`).
- Security fixes are the exception. Dependabot security updates are enabled and are not delayed by the cooldown.

## Secrets

Never commit `.env` files, database credentials other than the local development defaults, or real API keys. Use obviously fake keys (like `demo-key`) in tests and docs.

## Security

Report vulnerabilities privately. See [SECURITY.md](SECURITY.md).
